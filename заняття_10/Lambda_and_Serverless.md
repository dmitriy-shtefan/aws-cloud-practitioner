# **Заняття 10 — AWS Lambda & Serverless**

---

## **1. Server-based проти Serverless Compute**

При проєктуванні архітектури у хмарі важливо обрати правильний підхід до управління обчислювальними ресурсами:

*   **Server-based Compute** (Обчислення на базі серверів):
    *   Клієнт орендує віртуальні машини (наприклад, **Amazon EC2**), де він повинен самостійно визначати кількість необхідних **vCPUs** та обсяг оперативної пам'яті (**RAM**).
    *   Головний недолік полягає в тому, що ви продовжуєте платити за сервери, навіть коли вони простоюють або використовуються не на повну потужність (underutilized).
*   **Serverless Compute** (Безсерверні обчислення):
    *   Провайдер повністю бере на себе управління фізичними серверами, операційними системами, контейнерами, мережею та масштабуванням.
    *   Такі сервіси за замовчуванням є **highly available** (високодоступними), **highly durable** (високонадійними) та еластично масштабуються.
    *   **Pay-for-value**: ви платите виключно за час фактичного виконання вашого коду (обчислень) і можете масштабувати споживання до нуля (**scale to zero**), тобто не платити нічого, коли сервіс не використовується.
    *   **Cold Starts** (Холодні старти): оскільки безсерверна інфраструктура запускає віртуальні машини лише в момент надходження запиту, перший запуск коду може вимагати додаткового часу на розігрів («spin up»), що іноді сповільнює обробку початкових запитів.

## **2. AWS Lambda Functions**

**AWS Lambda** — це флагманський безсерверний FaaS-сервіс (Function as a Service) від AWS.

*   **Область відповідальності**: Ви відповідаєте виключно за свій код та дані. AWS повністю керує розгортанням, запуском, оновленням безпеки ОС та масштабуванням інфраструктури.
*   **Принцип роботи**: Ви завантажуєте невеликі фрагменти коду (функції). Для великих проєктів код завантажується у вигляді **ZIP-архіву** або посиланням на **Amazon S3**. Lambda також підтримує розгортання кастомних контейнерів.
*   **Гнучке налаштування**: Для кожної функції ви можете вручну встановити ліміт пам'яті (**Memory**) та максимальний час роботи (**Timeout**), після якого виконання примусово зупиниться.
*   **Тарифікація**: Плата стягується на основі кількості запитів та часу виконання функції, який округляється до найближчих **100 мілісекунд**.

## **3. Ключові концепції: Runtime, Event, Trigger та Invocation**

Для роботи з AWS Lambda необхідно розуміти чотири базові терміни:

1.  **Runtime** (Середовище виконання) — це мовне середовище (наприклад, **Node.js, Python, Ruby, PowerShell**), яке використовує Lambda для запуску вашого коду. AWS підтримує як стандартні готові рантайми, так і запуск власних через контейнери.
2.  **Event** (Подія) — це дані, представлені у вигляді **JSON-об'єкта**, які передаються у функцію під час запуску. Цей об'єкт містить корисне навантаження (payload) з інформацією, яку код має обробити (наприклад, ім'я користувача чи параметри запиту).
3.  **Trigger** (Тригер) — це джерело події (інший сервіс AWS, наприклад, **Amazon S3**, **API Gateway** чи **SQS**), яке автоматично ініціює запуск вашої Lambda-функції при виникненні певної події.
4.  **Invocation** (Виклик) — безпосередній запуск (виконання) коду функції у відповідь на подію. Виклики можуть здійснюватися автоматично тригерами або вручну для тестування (наприклад, через тестовий payload у консолі).

---

## **4. Lambda Execution Roles**

Для того, щоб ваша Lambda-функція могла легітимно взаємодіяти з іншими ресурсами AWS (наприклад, зчитувати файли з бакета S3 або записувати дані в таблицю DynamoDB), їй необхідні відповідні права доступу.

*   Права надаються шляхом створення та прив'язки до функції спеціальної **IAM Role** (ролі виконання).
*   Ця роль не використовує статичні паролі чи секретні ключі, а забезпечує тимчасові безпечні токени для авторизації API-викликів усередині хмари AWS.

---

## **5. Моніторинг: Amazon CloudWatch Logs**

Кожен запуск Lambda-функції автоматично реєструється в системі моніторингу AWS.

*   **Автоматичне логування**: Усі виведення вашого коду (наприклад, результати тестування чи повідомлення про помилки) автоматично записуються та надсилаються в **Amazon CloudWatch Logs**.
*   **Структура логів**: Для кожної Lambda-функції створюється окрема лог-група (**Log Group**), яка містить у собі потоки логів (**Log Streams**), названі відповідно до запущених інстанцій функцій з точними часовими мітками (timestamps).

## **6. Порівняння Amazon EC2 та AWS Lambda**

| Характеристика | Amazon EC2 | AWS Lambda |
| :--- | :--- | :--- |
| **Тип обчислень** | Server-based (віртуальні машини). | Serverless (функції як сервіс). |
| **Управління** | Ви керуєте операційною системою (Guest OS), ПЗ та патчами. | AWS повністю управляє ОС, рантаймом та патчами. |
| **Масштабування** | Ручне або через налаштування Auto Scaling Groups (ASG). | Автоматичне, миттєве та безшовне під навантаження. |
| **Доступність (HA)** | Потребує ручного проєктування (Multi-AZ, балансувальники). | Висока доступність (High Availability) вбудована за замовчуванням. |
| **Модель оплати** | Погодинна або посекундна оплата за роботу сервера, навіть коли він простоює. | Оплата тільки за мілісекунди роботи коду; нуль витрат при простої. |
| **Часові обмеження** | Може працювати безперервно 24/7. | Обмежена максимальним часом виконання (Timeout) однієї функції. |

## **7. Огляд сервісів інтеграції додатків (Application Integration)**

У сучасних мікросервісних та безсерверних архітектурах додатки мають бути максимально незалежними та слабкозв'язаними (**loosely coupled**). Для забезпечення їхньої взаємодії AWS пропонує кілька ключових інтеграційних сервісів:

```
                  ┌─────────────────────────────────────────┐
                  │          APPLICATION INTEGRATION        │
                  └────────────────────┬────────────────────┘
                                       │
     ┌──────────────────┬──────────────┴───┬────────────────────┐
     ▼                  ▼                  ▼                    ▼
┌──────────┐       ┌──────────┐       ┌──────────┐       ┌─────────────┐
│ API GW   │       │   SQS    │       │   SNS    │       │ EventBridge │
│ (Front   │       │ (Message │       │ (Pub/Sub │       │ (Serverless │
│ Door)    │       │ Queue)   │       │ Push)    │       │ Event Bus)  │
└──────────┘       └──────────┘       └──────────┘       └─────────────┘
```

### **Amazon API Gateway**
*   **Визначення**: Повністю керований сервіс, який дозволяє розробникам створювати, публікувати та захищати HTTP, REST та WebSocket API у будь-якому масштабі.
*   **Роль у системі**: Виступає як єдина точка входу («front door») для мобільних та вебдодатків, перенаправляючи запити користувачів на відповідні бекенд-сервіси (наприклад, AWS Lambda, сервери EC2 або бази даних).
*   **Функції**: Забезпечує контроль трафіку (throttling), авторизацію користувачів, логування запитів та перетворення форматів.

### **Amazon SQS (Simple Queue Service)**
*   **Визначення**: Повністю керований сервіс черг повідомлень (**message queueing service**) для асинхронного зв'язку.
*   **Принцип роботи**: Працює за моделлю **Pull** (отримувачі мають самостійно опитувати чергу через API/SDK для отримання нових повідомлень). Повідомлення зберігаються в черзі до **14 днів** і автоматично видаляються після успішної обробки споживачем.
*   **Сценарії**: Декопуляція мікросервісів, фонова обробка важких завдань (наприклад, черги транзакційних листів).

### **Amazon SNS (Simple Notification Service)**
*   **Визначення**: Повністю керований сервіс обміну повідомленнями за моделлю **Pub/Sub (Publish/Subscribe)**.
*   **Принцип роботи**: Працює за моделлю **Push** — щойно видавець (publisher) надсилає повідомлення в тему (**Topic**), SNS миттєво та автоматично розсилає (проштовхує) його всім підписаним клієнтам (**Subscribers**).
*   **Канали доставки**: Може надсилати повідомлення на Lambda, черги SQS, HTTP/S вебхуки, а також у вигляді SMS-повідомлень чи простих текстових листів (plain text emails, наприклад, для сповіщень про фінансові бюджети).

### **Amazon EventBridge (раніше CloudWatch Events)**
*   **Визначення**: Безсерверна шина подій (**serverless event bus**), яка допомагає пов'язувати додатки за допомогою даних, що генеруються різними сервісами AWS, вашим власним кодом або сторонніми SaaS-платформами.
*   **Принцип роботи**: Отримує події в реальному часі від джерел (producers), оцінює їх на основі заданих вами правил (**Rules**) і автоматично направляє у відповідні цільові сервіси-мішені (**Targets**, наприклад, запускає Lambda-функцію).
*   **Особливість**: Кожен акаунт AWS за замовчуванням отримує одну стандартну шину подій (**default event bus**), але ви можете створювати власні кастомні або інтегрувати партнерські SaaS-шини.
